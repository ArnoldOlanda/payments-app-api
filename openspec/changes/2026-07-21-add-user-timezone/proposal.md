# Proposal: Per-user timezone (IANA) for range computation and display

## Why

`analytics.service.ts` and `report.service.ts` call `dayStart(new Date())` / `dayEnd(new Date())` / `weekStart(new Date(), 1)` / `weekEnd(new Date(), 1)` from `@formkit/tempo`. These functions use the Node process TZ, which is set at deploy time on the VPS container. As a result:

- "Today" for an operator in `America/Argentina/Buenos_Aires` (UTC-3) is computed at the UTC boundary, not the local one. Cobranzas del día crosses ~3 hours into the previous or next day from the operator's perspective.
- "This week" starts on Monday in the operator's locale — but currently starts in the container's TZ.
- Server-generated PDFs (`report.service.getFichaPagos`) display dates without any TZ awareness.

The DB already stores everything as `TIMESTAMP WITH TIME ZONE` normalized to UTC (see migration `1784692166761-MigrateAuditFieldsToTimestamptz.ts`), so the persistence layer is correct. The leak is purely in **range computation** and **server-side display formatting**.

There is a `zone` table and `users_zone` M2M in the schema, but it represents a **business zone** (sucursal / regional assignment for access control), not a personal IANA timezone. This proposal does not touch that table.

## What Changes

- New column `timezone varchar(64) NOT NULL DEFAULT 'UTC'` on `user`. Stores an IANA tz identifier (e.g. `America/Argentina/Buenos_Aires`).
- A TypeORM migration generated via `yarn migration:generate` that adds the column and backfills `'UTC'` for existing rows. Reversible via the standard `down`.
- Auth pipeline reads the `X-Timezone` request header on every request, validates it as IANA, persists it on the user row lazily (only when present and changed), and embeds `timezone` as a JWT claim. Falls back to the stored value when the header is absent.
- New endpoint `PATCH /users/me/timezone` updates the user's timezone. Per user decision, **no JWT rotation** is returned — the new TZ applies on the next login (Option A).
- New `@CurrentTimezone()` parameter decorator extracts `req.user.timezone` from the authenticated request.
- `analytics.service.ts` and `report.service.ts` pass `timeZone: tz` to every `dayStart` / `dayEnd` / `weekStart` / `weekEnd` / `format` call that represents a user-facing range or display.
- A `src/common/datetime/tempo.ts` thin wrapper centralizes the `@formkit/tempo` calls and guarantees the `timeZone` option is always applied — preventing future drift.
- Validation helper `assertIanaTimezone(tz)` using `Intl.DateTimeFormat` rejects unknown identifiers with `400 Bad Request`.
- API responses stay in ISO UTC. Client-side formatting is the consumer's responsibility. Server-generated PDFs (`report.service`) format dates in the user's TZ using the wrapper.

## Impact

- **API behavior change.** "Today" and "This week" boundaries in analytics/reports now follow the user's timezone instead of the container's. Existing reports generated before the deploy will look ~3 hours off for non-UTC operators; new ones will be correct.
- **Auth payload change.** JWT now carries `timezone`. Existing tokens remain valid until expiry; new tokens carry the claim. `JwtStrategy.validate` returns `timezone` on the `Actor`.
- **Header dependency.** Clients (web, mobile) must send `X-Timezone` from day one. Without it, the API falls back to the user's stored value (initially `'UTC'` for legacy users). No silent override.
- **New endpoint.** `PATCH /users/me/timezone` is available to every authenticated user regardless of role.
- **Performance.** No measurable cost. One extra `varchar(64)` column, no new index.
- **DB schema change.** Adds one column. Migration is reversible via the standard `down`.

## Out of Scope

- `customer.timezone`. Customers are debtors; users are operators. If customer-facing flows (notifications, due-date reminders) need per-customer TZ, it is a separate change.
- Automatic DST transition tests. Trust `@formkit/tempo` and the IANA tz database.
- Client-side (web/mobile) implementation. Out of scope for the API change-set. The API contract is the deliverable. Web/mobile send `X-Timezone` and format locally; that work is tracked separately.
- JWT rotation on `PATCH /users/me/timezone`. Per user decision (Option A: applies on next login).
- Refactoring the `zone` business-zone concept. Unrelated.

## Acceptance Criteria (draft; finalized in `spec`)

- A user row has `timezone` column with default `'UTC'`.
- Migration is reversible: `up` adds column with default `'UTC'`; `down` drops the column.
- `X-Timezone: America/Argentina/Buenos_Aires` header on an authenticated request persists the value on the user row when it differs (idempotent).
- `X-Timezone: Mars/Olympus_Mons` (invalid) returns `400 Bad Request`; the user row is not modified.
- `X-Timezone` header omitted on subsequent requests → no DB write; the stored value continues to be used.
- Login response JWT includes `timezone` claim equal to the user's stored value.
- `JwtStrategy.validate` returns `Actor & { timezone }`.
- `PATCH /users/me/timezone` with a valid IANA identifier returns `200 { timezone }` and updates the row; no new token is issued.
- `PATCH /users/me/timezone` with an invalid identifier returns `400 Bad Request`.
- `analytics.service.getKpis(tz)` uses `tz`: a user with `timezone = Asia/Tokyo` at UTC `2025-06-15T15:00:00Z` (which is `2025-06-16T00:00 JST`) gets `dayStart = 2025-06-15T15:00:00Z` — verified by unit test.
- `report.service.getDaysWeek(tz)` returns 7 dates starting on Monday in the actor's locale.
- `report.service.getFichaPagos(tz)` PDF generation formats dates with the actor's TZ via the wrapper.
- Invalid IANA rejection path is unit-tested (offset syntax, empty, unknown zone).
- `grep -r "@formkit/tempo" src/` after the change returns only `src/common/datetime/tempo.ts`.
- Existing analytics/report/auth tests that assumed container TZ are updated to inject an explicit TZ.
- `yarn lint` and `yarn test` pass; `yarn test:e2e` passes (or skipped with explicit user approval per repo convention).
